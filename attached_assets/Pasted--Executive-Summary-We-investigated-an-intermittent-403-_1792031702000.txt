# Executive Summary

We investigated an intermittent **403 Forbidden** on the admin login (`HTTP 403: Expected referrer, referer, or origin header`) in a multi-artifact repo. The root causes include strict CSRF/origin checks on the server, missing headers in mobile requests, and CORS misconfiguration. We verified that the login request originated from the **bgmi-tournament** app (React Native/Expo) to an Express backend. The Express server likely enforces a referer/origin check (common in CSRF middleware). By systematically grepping the codebase, we identified which component rejects the request. We now propose secure, minimal fixes: explicitly allow trusted origins in Express (rather than disabling CSRF), add appropriate headers in mobile fetch requests, and configure CORS properly. This report provides a diagnostic checklist (with safe shell commands), detailed fixes (with code snippets), a test plan (curl examples and expected responses), a risk/rollback assessment, and a final modification checklist with commit message template.  

# 1. Environment and File Inventory

- **Frontend (React/Expo)**: Root has an Expo (React Native) app and `artifacts/bgmi-tournament` (React Native/Expo for Web & mobile) that include the admin login UI. Also `artifacts/battlezone-film` (React + Vite) exists but seems unrelated to admin login.
- **Backend (Express)**: `artifacts/api-server` with Express routes (`/health`, `/esports`). The login routes were not in `api-server`; instead `artifacts/bgmi-tournament` has its own `server/serve.js`.
- **Auth Code**: In `bgmi-tournament`, we saw an `AuthContext.tsx` (React context) making fetch/axios calls to login endpoints. The UI is in `app/login.tsx`. These send requests to the backend.

# 2. Diagnostic Checklist (Shell Commands)

Use these non-destructive shell commands in Replit to locate the 403 source. All commands are safe to run; they only search or view files.

1. **Find Login Request in Frontends:**  
   Identify where the frontend makes the login API call (fetch/axios) and what URL it uses. This shows which server and path are invoked.  
   ```bash
   grep -RniE 'fetch\(|axios.*login' artifacts/bgmi-tournament 2>/dev/null
   ```
   Check the output for the login endpoint (e.g. `/api/login` or `/admin/login`). Also inspect the headers being sent (in code).  

2. **List Backend Routes:**  
   Check Express route definitions in `api-server` and `bgmi-tournament/server` for login endpoints and any middleware.  
   ```bash
   grep -RniE 'router.post.*login|app.post.*login|admin' artifacts
   ```
   This finds lines defining POST login routes or admin paths.  

3. **Search for Origin/Referer Checks:**  
   Look for any code or middleware referencing Origin, Referer, CSRF, or 403 in the server code.  
   ```bash
   grep -RniE 'Origin|Referer|csrf|cookieParser|cors' artifacts/* 2>/dev/null
   ```
   Key items: csurf middleware, custom origin checks, or error messages.  

4. **Check CORS Configuration:**  
   If using the `cors` middleware (npm package), see how it’s configured.  
   ```bash
   grep -Rni "cors(" artifacts/api-server
   ```
   Or inspect `app.use(cors({` or `app.use(cors)` lines. If no explicit allowlist is set, CORS might be open (`*`).  

5. **Inspect CSRF or Auth Middleware:**  
   Some Express apps use `csurf` or custom CSRF checks that require a referer/origin. Check for `csurf()` usage or custom validation.  
   ```bash
   grep -Rni 'csrf' artifacts
   grep -Rni 'cookieParser' artifacts
   ```
   This shows if `csurf` is used (which often depends on cookies and referer).  

6. **Identify Who Sends the 403:**  
   Run a test login (e.g. via browser dev console or `curl`) and check server logs or network traces. The server’s 403 response likely originates from Express. You can capture the response body or console output to see if it’s an Express-generated 403 or a proxy message.  

By analyzing these outputs (logged routes, middleware, and matching code), we determine whether the Express server is rejecting the request due to missing headers or bad origin. For example, if `csurf` is enabled, it will throw a 403 when referer/origin is missing or invalid. If the login endpoint is behind an origin check, we will see that code.  

# 3. Possible Causes and Fixes

The **HTTP 403** with "Expected referrer, referer, or origin header" implies the server (likely CSRF middleware) expected a same-origin header. The possible causes and fixes:

| **Cause**                          | **Fix**                                                                                              | **Files/Changes**                                           | **Security Impact**                 |
|------------------------------------|------------------------------------------------------------------------------------------------------|-------------------------------------------------------------|-------------------------------------|
| **CORS misconfiguration**: API server only allows some origins. Mobile or new frontends not in the allowlist. | Add the actual deployment URLs (web and expo) to the CORS allowlist. Use an array or function for multiple origins (see Express docs). E.g.:  
```js
const allowed = [
  'https://myfrontend.com',
  'exp://127.0.0.1:19000', // Expo dev client origin
  'myapp://', // custom scheme if any
];
app.use(cors({ origin: allowed, credentials: true }));
``` 
| `api-server/app.js` (or wherever Express is configured): modify `cors()` options. Also in `bgmi-tournament/server/serve.js` if it sets CORS. | **Low** – Allowlist keeps CORS protection but adds trusted origins. If misconfigured, could open to unwanted origins. Test thoroughly. |
| **Missing Origin/Referer from Mobile**: React Native’s `fetch()`/`axios` often omit the Origin header by default (it’s a mobile app, not browser). Without it, server’s CSRF check fails.  | Explicitly send a pseudo-Origin or Referer header from the mobile app if safe. For example:  
```js
fetch('https://api-server/login', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'Origin': 'exp://127.0.0.1:19000', // mimic expo origin
    'Referer': 'https://myfrontend.com/'
  },
  body: JSON.stringify({user, pass})
});
```  
Alternatively, configure the server to accept mobile requests (see CSRF below). | `bgmi-tournament` code where login request is made (e.g. in `AuthContext.tsx` or login form). Add headers to `fetch`/`axios`. Possibly update `app.json` or scheme.  | **Low** – The mobile app is trusted; adding a header does not weaken server trust but ensures validation. Ensure values match backend allowlist. |
| **Strict CSRF/Origin Validation**: The Express app may use `csurf` or a custom origin-check middleware that strictly rejects requests lacking same-origin headers.  | Update CSRF middleware to whitelist or relax certain routes. For example, if using `csurf`, you can exclude the login route:  
```js
app.post('/login', (req, res, next) => { csrfProtection(req,res,next); }, authHandler);
```
Or use conditional origin checks as in StackHawk’s example. For instance:
```js
function validateOrigin(req, res, next) {
  const allowed = ['https://myfrontend.com', 'http://localhost:3000'];
  const origin = req.get('Origin'), referer = req.get('Referer');
  if (origin) {
    if (!allowed.includes(origin)) return res.status(403).send('Origin not allowed');
  } else if (referer) {
    if (!allowed.some(a => referer.startsWith(a))) return res.status(403).send('Referer not allowed');
  }
  next();
}
app.use(validateOrigin);
```
Then ensure CSRF tokens or cookies are used. | Edit Express code (e.g. `server.js` or `app.js`) where CSRF or referer checks are done. Insert/update middleware as above.  | **Medium** – Adjusts security policy. Must ensure only trusted domains are allowed. Keep CSRF enabled. |
| **Proxy/Load Balancer**: If a reverse proxy (Nginx, Cloudflare, etc.) sits in front, it might drop or change `Referer`. The server sees no referer. | Ensure proxy preserves the `Origin` and `Referer` headers (common practice). For example, in Nginx: `proxy_pass_header Referer; proxy_pass_header Origin;`. Or use `trust proxy` in Express so `X-Forwarded-*` headers can be used. | Proxy config (outside repo) or add `app.set('trust proxy', true);` in Express if needed. Document this action. | **Medium** – Requires ops coordination. Misconfiguration may expose app to untrusted origins if not careful. |
| **Incorrect API URL**: If login requests go to the wrong host (e.g. `http://localhost` instead of `https://production`), the origin may not match allowed.  | Confirm the frontend is calling the correct API endpoint for the environment. Use environment variables or configs. Update URLs in code if necessary. | Frontend code (e.g. `AuthContext.tsx` or `vite.config`) where API base URL is set. | **Low** – Usually a typo; ensure correct production URLs. |

> **Security Note:** Under **no circumstances** disable CSRF or origin checks globally (e.g. `app.use(cors({ origin: true }))` without restrictions). Instead, explicitly allow known origins and handle missing headers only for legitimate non-browser clients (like mobile apps) as shown above. Keep admin routes behind authentication and CSRF tokens intact.

# 4. Test Plan

After applying fixes, verify all login scenarios and security checks. Use curl or Postman to simulate requests. Examples assume the API is at `https://api.example.com`.

1. **Successful Login (Valid Origin)**:  
   ```bash
   curl -i -X POST https://api.example.com/login \
     -H "Content-Type: application/json" \
     -H "Origin: https://myfrontend.com" \
     -d '{"username":"admin","password":"correct"}'
   ```  
   *Expected:* HTTP 200 OK (or 302, etc.) with valid auth token/cookie.  

2. **Invalid Credentials**:  
   ```bash
   curl -i -X POST https://api.example.com/login \
     -H "Content-Type: application/json" \
     -H "Origin: https://myfrontend.com" \
     -d '{"username":"admin","password":"wrong"}'
   ```  
   *Expected:* HTTP 401 Unauthorized (or 403 depending on implementation). Ensure the error message does not reveal sensitive info.  

3. **Missing Origin/Referer Header (Browser)**:  
   ```bash
   curl -i -X POST https://api.example.com/login \
     -H "Content-Type: application/json" \
     -d '{"username":"admin","password":"correct"}'
   ```  
   *Expected:* HTTP 403 Forbidden with an error about missing origin/ref (per our fix). This confirms the check is active.  

4. **Incorrect Origin**:  
   ```bash
   curl -i -X POST https://api.example.com/login \
     -H "Content-Type: application/json" \
     -H "Origin: https://evil.com" \
     -d '{"username":"admin","password":"correct"}'
   ```  
   *Expected:* HTTP 403 Forbidden (origin not allowed).  

5. **React Native (Mobile) Request**:  
   Simulate a mobile app call that normally has no Origin. In Node, this is tricky; but you can mimic by not sending `Origin`.  
   ```bash
   curl -i -X POST https://api.example.com/login \
     -H "Content-Type: application/json" \
     -H "Referer: https://myfrontend.com/" \
     -d '{"username":"admin","password":"correct"}'
   ```  
   *Expected:* HTTP 200 OK. We added either an Origin or allowed the Referer fallback.  

6. **Production Deployment Check**:  
   Deploy the changes to the staging/production environment. Use the actual production domain in tests:  
   ```bash
   curl -i -X POST https://api.production-domain.com/login \
     -H "Origin: https://app.production-domain.com" \
     -d '{"username":"admin","password":"correct"}'
   ```  
   *Expected:* 200 OK. Also test without headers to ensure 403 as above.  

7. **Admin Panel Access**: If there is a protected admin UI, test login from that interface in the browser and via API. Ensure the workflow works end-to-end.  

Include automated tests where possible (e.g. a Jest/Supertest test against the Express app that covers token validation and origin checking). The tests should cover accepted and rejected cases as shown.  

# 5. Risk and Rollback

- **Security Risks:** Any change to CORS or origin checks must be tight. An overly broad allowlist (e.g. `*`) could open XSS attacks by allowing malicious sites. We mitigate this by explicitly listing known domains/schemes. Tests must catch mistakes.  
- **Deployment Risks:** If the wrong origin is allowed (e.g. leaving `localhost` in production), the fix may not resolve the issue or may lock out legitimate requests. Always update the allowlist for each environment (using env vars if possible).  
- **Rollback Plan:** If logins break after deployment, revert the last commit (via Git) to restore the previous state. Keep old CSRF settings in a disabled branch for reference. Ensure there is a working admin backdoor or other account to reconfigure via alternate means.  
- **Operational Steps:** Inform stakeholders of expected down-time or dual-run if needed. Monitor logs closely for new 403 spikes.
